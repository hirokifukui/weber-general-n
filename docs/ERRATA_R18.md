# ERRATA_R18 — corrections made in r18 against the sealed r17 (2026-08-26)

No mathematical erratum: the GPT r17 review accepted the three R17 gates (relative norm one, spectral rank for every (n, r),
improvement over MO2016 Theorem A in both classes) and found no error in the mathematics. Three ARTIFACT errata, all mine.

- E18-1 (release integrity: zip != verified tree). The sealed r17 zip (SHA256 3a0b9bfb…6dd2) lacked twelve files listed in
  MANIFEST_SHA256.txt: archive/rounds/r12/main_R12.{aux,out,toc}, sage/family_ky1000/driver_0{0..5}.out, sage/family_ky1000/
  verify_driver.out, sage/family_ky1000_r11_clean/driver.out, sage/family_survey/driver.out. Cause: the manifest was generated on
  the working tree, the full verifier was run on that tree, and the zip was then produced through an exclusion list (*.aux, *.out,
  *.toc, ...) that also dropped nohup `.out` logs the manifest listed. The uploaded package was therefore not the tree that had
  passed verification. Repair: RELEASE_STATUS.md "Release protocol, r18 revision" — a staging tree is built first (by-products and
  nohup logs removed), the manifest is generated ON the staging tree (missing 0 / unlisted 0 hard gate), the full verifier runs on
  the staging tree, the tree is zipped as is, re-extracted, and the manifest is checked again on the re-extracted copy. (GPT r17 sect 6.)
  The first execution of that protocol caught a further defect of the same kind: Sage preparse by-products (*.sage.py) embed the ABSOLUTE
  path of their source in a header comment, so the copy regenerated by the verifier on the staging tree differed from the copy shipped
  from the vault (scripts/family_verify.sage.py MISMATCH after the run). Such files are path-dependent and cannot be in a portable
  manifest: tools/gen_manifest.py now skips *.sage.py everywhere and the staging tree excludes them; the r17 zip contained them (they
  matched only because the r17 verifier ran inside the vault).
- E18-2 (trust label C overstated for the p = 3 certificate). In r16/r17 CERT_D3 carried the label C while tools/check_p3_cert.py only
  checked the JSON's internal consistency, the producer-script hash, the stored 40-digit endpoints and the improvement flags; nothing
  was recomputed from the definitions, so the "certificate" was a producer record with a small consistency checker, not a read-only
  replay. Moreover the stored endpoints were 40-digit strings rounded to nearest, so the enclosure reconstructible from the JSON was
  the 40-digit interval, not the 1e-800 ball, and a nearest-rounded "lo" string can exceed the true lower endpoint. Repair: certificate
  format v2 (exact dyadic outward endpoints, radius, precision, rounding mode, directed decimals; routes and their intersection in
  separate fields) and scripts/verify_p3_readonly.sage (verifier step 04f), which rebuilds eta_n, all conjugate logarithms, both
  covolume routes, the floor, C^{(3)}_{n,r} and G(3,s,f) from the definitions at 4000 bits, compares by intersection with the shipped
  exact intervals, re-decides the improvement from its own balls, and rejects five planted certificates. The label C of CERT_D3 now
  rests on that replay. (GPT r17 sect 5, items 12-44.)
- E18-3 (current-facing metadata stale). CITATION.cff / .zenodo.json pointed to main_R16.pdf; the PDF subject said r16; the Blueprint
  title said r15 and its legend "package r16"; the paper's comment header, trust-table caption and artifact index referred to
  BLUEPRINT_MAP_R16 / CLAIMS_R16 / blueprint_r16.pdf / STATEMENT_FREEZE_R15 / ERRATA_R15; the README summary line still carried the
  withdrawn r16 P3 constants. tools/check_release_metadata.py synchronized only the version line. Repair: all pointers synchronized to
  the current round; round numbers removed from the submission-facing PDF subject and Blueprint title (version lives in CITATION.cff /
  .zenodo.json only); the gate extended to the notes / identifier fields, the paper body, print.tex and the README line. (GPT r17 sect 7.)

Also withdrawn as wording (not errata): "best published uniform bound" (the comparator is named: the uniform-in-n bound of
Morisawa--Okazaki, MO2016 Thm A; no novelty audit has been completed), "two independent routes" ("two independent linear-algebraic
routes from the same log profile"), and the trust labels in theorem titles (now only in the trust table, CORRESPONDENCE.csv and the
Blueprint).
